# 問30｜gRPCストリーミング（Streaming API）

## 目標
gRPCの「サーバーストリーミング」を使って、1回のリクエストに対してサーバーから複数回データを継続的に送信する方法を学び、上級コースを完結します。

## 今回の演習で学ぶこと
この問題では、1回のリクエストに対してサーバーから少しずつ複数回に分けて継続的にデータを送信する「サーバーストリーミング」の仕組みを、以下の3つの重要ポイントに注目して学び、上級コースを締めくくります。

**1. データの繰り返し処理（Range Loop）**
クライアントへ送りたい大量のデータ（長大なログファイルや巨大なリストなど）を順番に取り出す工程です。
```go
for _, l := range logs { // 膨大なログを1行ずつ取り出す
```
- 単発の通信（Unary）の場合、10万行のログがあればサーバーのメモリに10万行を全て溜め込んでからドンッと送らなければならず、サーバーがパンク（OOM：Out Of Memory）してしまいます。これを1行ずつ捌くためのループです。

**2. 逐次送信（Stream Send）**
全ての準備が整うのを待たず、1つでもデータができあがったら、さっさとクライアントへ「小包」として発送してしまう工程です。
```go
// 1行できたから、すぐ送る！（まるでベルトコンベア）
err := stream.Send(&LogResponse{Message: l})
```
- `stream.Send`: gRPCストリーミングの真骨頂です。1本の繋ぎっぱなしの専用トンネルを使って、データを何度でも（好きなタイミングで）小出しに送り続けることができます。
- クライアント側も「全部届く」のを待つことなく、1行受け取るたびに画面に表示できるため、「リアルタイムに文字が流れるコンソールログ」や「動画のパケット配信」のような爆速のユーザー体験が生まれます。

**3. 通信異常の即時中断（Error Check）**
小出しに送っている最中に、相手との通信が途切れたりしたトラブルに対処する工程です。
```go
if err != nil { // トンネルが崩落した（相手が切断した等）
    return err // ここで送信作業を完全にやめる
}
```
- 延々と送っている間にも、クライアント側がアプリを強制終了したり、トンネルに入って電波が途切れたりすることがあります。
- `Send` はその瞬間にエラーを返してくれるため、そこで「これ以上送っても無駄だ」と判断し、安全にループを抜け出して無駄なサーバーリソースの消費を食い止めます。




**ストリーミングが優れる場面**
巨大なファイルをダウンロードしたり、絶え間なく流れてくるログを表示したりする場合、一度に全てのデータをメモリに読み込んで送ろうとするとサーバーがパンクしてしまいます。ストリーミングを使えば、少しずつデータを流せるため、サーバーもクライアントも「少ないメモリ」で「大量のデータ」を効率よく扱うことが可能になります。
