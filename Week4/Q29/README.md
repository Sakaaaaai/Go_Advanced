# 問29｜gRPCのエラーハンドリングとステータスコード

## 目標
HTTPの404/403/500に相当する、gRPC専用のステータスコード（`codes`）を使って型安全なエラーを返す方法を学びます。

## 今回の演習で学ぶこと
この問題では、HTTPの404や500といったおなじみのエラーコードに相当する、gRPC専用の「ステータスコード」を使って、型安全なエラーのやり取りをする方法を、以下の2つの重要ポイントに注目して学びます。

**1. 入力値エラー（InvalidArgument）の返却**
クライアント（フロントエンド等）から送られてきたデータがいきなり不適切な場合に、門前払いにする工程です。
```go
if req.Id == "" {
    // 相手に「あなたの送ってきたデータが不備ですよ（ステータス400相当）」と伝える
    return nil, status.Error(codes.InvalidArgument, "id is required")
}
```
- HTTP通信と違い、gRPCでは `404` や `500` のような単純な数字ではなく、`codes` パッケージに用意された意味のある「ステータスコード名」を使ってエラーの種類を表現します。
- `InvalidArgument` は「送られてきた引数がおかしい」という意味で、通信の規約違反を相手に優しく（しかし厳密に）指摘します。

**2. データ未存在エラー（NotFound）の返却**
データベースを探したけれど、目的のデータが見つからなかったことを正しく伝える工程です。
```go
if err == sql.ErrNoRows { // Goの標準的な「レコード無し」エラー
    // 相手に「探したけど無かったよ（ステータス404相当）」と伝える
    return nil, status.Error(codes.NotFound, "user not found")
}
```
- サーバー内で起きた内部エラー（`err`）をそのままクライアントに投げるのは絶対NGです（内部の構造がバレるため脆弱性に繋がります）。
- 内部で起きた生々しいエラーを、gRPC専用の綺麗にラッピングされたステータスコード（`codes.NotFound` や `codes.Internal` など）に包み直してあげるのが、プロのAPI設計の第一歩です。クライアント側プログラムは、文字列ではなくこの「コード」を見て次にどうするかを機械的に（型安全に）判断できるようになります。




**安全なエラーハンドリング**
この仕組みを使うことで、クライアント側では「エラーメッセージの文字列を無理やり解析する（パターンマッチング）」といった脆い方法を避け、「スイッチ文でエラーの種類をスマートに判別する」という、バグが起きにくい明確な実装が可能になります。
