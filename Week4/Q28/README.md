# 問28｜分散トレーシング（OpenTelemetry）

## 目標
複数のマイクロサービスを経由するリクエストのボトルネックやエラーを特定する「分散トレーシング」の概念と、GoでのOpenTelemetry（OTel）を使ったSpanの作成方法を学びます。

## 今回の演習で学ぶこと
この問題では、複数のマイクロサービスを経由するリクエストの全体像を「線」として繋いで、ボトルネックやエラー箇所を特定する「分散トレーシング」の基礎を、以下の3つの重要ポイントに注目して学びます。

**1. 処理区間の開始宣言（Start Span）**
ストップウォッチのボタンを押して、計測したい処理単位（スパン）の「始まり」を宣言する工程です。
```go
// "FetchDatabase" という名前で計測用のストップウォッチ（スパン）を作る
ctx, span := tracer.Start(ctx, "FetchDatabase")
```
- 第1引数の `ctx` は、前の処理から受け継がれた「バトン」です。このバトンを繋いでいくことで、ユーザーの1回のクリックから発生した「AAPI→BAPI→データベース」という複数のサービスを股にかけた巨大な処理の流れ全体（トレース）を、一筆書きの線として繋ぐことができます。

**2. 終了予約と計測の完了（Defer End）**
ストップウォッチを止めて、所要時間を確定させる後片付けの工程です。
```go
defer span.End() // 関数が終わる時に必ずストップウォッチを止める
```
- `defer` を使うことで、途中でエラーが起きて関数を抜けようがパニックになろうが、確実に「いつこの処理が終わったか」を記録できます。これが無いと「永遠に終わらない処理」としてダッシュボードに表示されてしまいます。

**3. 異常発生時の記録（Record Error）**
計測データの中に「ここでエラーが起きた」という生々しい傷跡を残す工程です。
```go
if err != nil {
    span.RecordError(err) // ダッシュボード上で赤く表示させるための報告
}
```
- 通常のログファイルだけだと「エラーが出たことは分かるが、大元の原因（どのユーザーのどの操作から繋がっているのか）が分からない」という迷子状態になります。
- OTelによってSpanにエラー情報を紐づけることで、何万というログの中から一瞬で「原因となった特定の処理ブロック」を見つけ出すことができます。




**マイクロサービス時代の必須スキル**
多数のサービスが複雑に絡み合う現代のシステムでは、1つのリクエストがどこで詰まっているのかを探すのは至難の業です。分散トレーシングを導入すれば、リクエストの全行程が一本の線として可視化され、問題解決のスピードが劇的に向上します。

## 問題文
`main.go` の `___` の部分を埋めてプログラムを完成させてください。

1. `tracer.Start(ctx, "FetchDatabase")` でSpanを開始してください。
2. `defer span.End()` でSpanを確実に終了させてください。
3. エラー発生時に `span.RecordError(err)` を呼んでください。

## ヒント
- `ctx, span := tracer.Start(ctx, "操作名")` でSpanを開始
- `defer span.End()` は Start の直後に書く（パニックでも確実に終了）
