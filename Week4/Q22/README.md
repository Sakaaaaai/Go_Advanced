# 問22｜クリーンアーキテクチャ・層化アーキテクチャ

## 目標
アプリケーションを「ドメイン層」「ユースケース層」「インフラ層」に分けて、変更に強い疎結合な設計（クリーンアーキテクチャ）を学びます。

## 今回の演習で学ぶこと
この問題では、アプリケーションを「ドメイン層」「ユースケース層」「インフラ層」の3つに分けて、変更に強い設計を作る方法を、以下の3つの重要ポイントに注目して学びます。

**1. 誰にも依存しない「ドメイン層」**
アプリケーションの心臓部であり、ビジネスの絶対的なルール（型や構造）を決める層です。
```go
type User struct { // IDと名前を持たなければならない、というルール
    ID   string
    Name string
}
```
- この層は「MySQL」や「JSON」といった外部の技術的要素の名前を一切含んではいけません（`import "database/sql"` などは御法度です）。純粋に「私たちのビジネスにおけるユーザーとは何か」というデータ構造だけに集中します。

**2. 契約としての「リポジトリインターフェース」**
データの取得や保存に関する「こういう機能が存在すること」という【契約（取り決め）】だけを行う層です。
```go
type UserRepository interface {
    // どんな仕組みで探すかはともかく、IDを渡したらUserを返す機能があるべきだ
    FindByID(id string) (User, error)
}
```
- クリーンアーキテクチャの真骨頂です。インターフェースとして「箱の形」だけを定義しておくことで、中身がMySQLだろうがRedisだろうがCSVファイルだろうが、上位の層は一切気にせずにビジネスロジックを書けるようになります。

**3. ビジネスの流れを作る「ユースケース層」**
ドメインのルール（1）と、リポジトリの契約（2）を組み合わせて、「ユーザーがやりたいこと機能（ユースケース）」を表現する層です。
```go
type userUsecase struct {
    repo UserRepository // 中身が何かは知らないが、契約どおり動く道具を持っている
}

func (u *userUsecase) GetUser(id string) (User, error) {
    return u.repo.FindByID(id) // その道具を使って、ユーザーを探して返す
}
```
- ここでも特定のインフラ（データベース製品など）への依存が存在しないため、将来的にデータベースを別のものに入れ替える事態が発生しても、このユースケース層（ビジネスロジックの中核）のコードは指一本触れる必要がありません。これが「変更に強い設計」です。




**依存の向きが鉄則**
設計のコツは、矢印（依存）を常に「外側から内側へ」向けることです。このルールを守ることで、例えば将来的にデータベースを入れ替えることになっても、一番大切なビジネスロジック（ユースケース）を一行も書き換えずに済むようになります。

## 問題文
`main.go` の `___` の部分を埋めてプログラムを完成させてください。

1. `ID` と `Name` を持つ `User` 構造体を定義してください（ドメイン層）。
2. `FindByID(id string) (User, error)` を持つ `UserRepository` インターフェースを定義してください。
3. `UserRepository` を持つ `userUsecase` を定義し、`GetUser(id)` で `repo.FindByID` を呼ぶ实装をしてください。
