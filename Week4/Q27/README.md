# 問27｜CI/CDパイプライン（GitHub Actions）

## 目標
コードのプッシュをトリガーに、自動でテスト・ビルドを実行する「CI（継続的インテグレーション）」パイプラインを GitHub Actions の YAML ファイルとして定義する方法を学びます。

## 今回の演習で学ぶこと
この問題では、コードがプッシュされた時などをきっかけに自動でテストを実行する「GitHub Actions」のYAMLファイルの書き方を、以下の3つの重要ポイントに注目して学びます。

**1. 自動化のきっかけ（Trigger）の定義**
GitHubに対して、「いつ、この自動お掃除（テスト）ロボットを起動するか」を指示する設定です。
```yaml
on:
  push:                # ソースコードがアップロード(プッシュ)された時
    branches: ["main"] # しかもそれが「main」ブランチだった時
```
- この設定により、開発者がうっかりバグのあるコードを本番用の共有ブランチ（main）にマージしようとした瞬間、自動的にストップをかけることができます。「人間は必ずミスをするからシステムで弾く」という、CI（継続的インテグレーション）の最も基本的な思想です。

**2. 実行場所（Runs-on）の指定**
テストを実行するための「使い捨ての仮想パソコン」の種類を決める設定です。
```yaml
jobs:
  test:
    runs-on: ubuntu-latest # 最新のUbuntu Linuxマシンを用意して！
```
- 自分のパソコン（ローカル環境）では手元の設定のおかげで偶然動いていたコードも、このまっさらな「クラウド上のLinux」で動かしてみるとエラーになることがよくあります。「私の環境では動いたんですけど…」という言い訳をなくすための超重要ステップです。

**3. 具体的な手順（Steps）の記述**
用意した使い捨てパソコンにやらせることを、上から順に箇条書きで指示する工程です。
```yaml
steps:
  # ① まず、リポジトリからソースコードをパクッとダウンロード(チェックアウト)してくる
  - uses: actions/checkout@v3
  # ② なにもないUbuntuに、指定したバージョンのGo言語をインストールする
  - uses: actions/setup-go@v4
    with:
      go-version: "1.20"
  # ③ いよいよ本命。Goのテストコマンドを実行し、一つでも落ちたらエラーにする
  - run: go test ./...
```
- `uses` は世界中の誰かが作ってくれた「便利ツール（Action）」をそのまま流用できる仕組みです。これらをレゴブロックのように組み立てることで、誰でも簡単にプロ級の自動化パイプラインが構築できます。




**チームの「番人」としてのアクション**
チーム開発では、誤って壊れたコードを合体させてしまうのを防ぐため、この自動パイプラインが「番人」となります。テストが通らない（赤信号）コードはマージできないように設定することで、常に健康なコードベースを保つことができます。

## 問題文
定数 `GitHubActionsYaml` にGitHub ActionsのYAML文字列を完成させてください：

1. `main` ブランチへの `push` と `pull_request` をトリガーに設定してください。
2. `runs-on: ubuntu-latest` で実行環境を指定してください。
3. `checkout`, `setup-go (v1.20)`, `go mod download`, `go test ./...` の各ステップを追加してください。

### 実行方法
```bash
cd /workspaces/Go_Advanced/Week4/Q27
go run main.go
```

### テストでの確認
```bash
cd /workspaces/Go_Advanced/Week4/Q27
go test main.go main_test.go
```
## ヒント
- `on: { push: { branches: ["main"] }, pull_request: {} }` の形
- ステップは `-name: 名前\n  run: コマンド` または `-uses: アクション名` の形
