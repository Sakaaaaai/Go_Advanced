# 問24｜モックを用いた複雑なテスト

## 目標
外部依存（DBや外部API）を持つコードをテストする際に「モック（Mock）」を使って、環境に依存しない高速で安定したユニットテストを書く方法を学びます。

## 今回の演習で学ぶこと
この問題では、本格的なデータベースを使わずに「偽物の道具（モック）」を身代わりにしてテストを行う方法を、以下の3つの重要ポイントに注目して学びます。

**1. 関数型フィールドを持つモック構造体**
クリーンアーキテクチャの真髄「インターフェース」の性質を利用して、本物のデータベースの「ダミー（影武者）」を作る工程です。
```go
type MockRepo struct {
    // どんな関数でも入れられる「空の箱」を用意しておく
    MockGetUser func(id string) (User, error)
}

// インターフェースを満たすためのメソッド
func (m *MockRepo) GetUser(id string) (User, error) {
    return m.MockGetUser(id) // 中身はただ空の箱に入った関数を実行するだけ
}
```
- この `MockRepo` はデータベースとは一切繋がりませんが、`UserRepository` インターフェースの形（`GetUser` メソッド）を満たしているため、上位層（ユースケース）からは本物に見えます。

**2. テストケースごとの振る舞いの注入**
空の箱に入れていた関数の中身を、テストケースの目的に合わせて「都合よく」書き換える（知能を注入する）工程です。
```go
mock.MockGetUser = func(id string) (User, error) {
    // データベースが手元になくても、「アリスがDBにいたこと」にできる！
    return User{ID: "1", Name: "アリス"}, nil
}
```
- 成功させたいテストでは「成功したデータ」を返し、エラー時のテストでは自作の「エラー」を返させます。これにより、本物のDBを用意しなくても「もしDBが落ちたらアプリはどう動くか」といったテストが簡単に書けます。

**3. 外部に頼らない独立したテスト**
作り上げた影武者（モック）を、DI（依存性の注入）を使ってアプリ本体へ潜り込ませてテストを実行する工程です。
```go
usecase := NewUsecase(mock) // 本物のDBの代わりにモックを渡す！
u, _ := usecase.GetUser("1")
```
- ネットワークも実際のファイル読み書きも発生しないため、テストの実行時間は限りなくゼロ（爆速）になります。
- 外部要因（DBが重い、データが変わったなど）でテスト結果がぶれることがなくなり、純粋に「自分の書いたビジネスロジックが正しいか」だけを安定して検証できる「ユニットテスト（単体テスト）」が完成します。




**テストピラミッドの土台**
こうしたモックを使ったユニットテストは、実行速度が非常に速いため、大量に書いて毎日何度も動かすのに適しています。品質管理のピラミッドにおいて、最も多く、最も頑丈であるべき「土台」の部分がこのユニットテストです。

## 問題文
`main.go` の `___` の部分を埋めてプログラムを完成させてください。

1. `MockGetUser func(id string) (User, error)` フィールドを持つ `MockUserRepository` を定義して `GetUser` を実装してください。
2. `main` 内で「id="1"なら Alice を返し、それ以外はエラー」の振る舞いをモックにセットしてください。
