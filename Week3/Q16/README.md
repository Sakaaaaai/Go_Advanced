# 問16｜gRPCサーバーの実装

## 目標
Protobufから自動生成されたGoインターフェースを実装する形でgRPCサーバーを作成し、クライアントからの呼び出しに応じた処理を返す方法を学びます。

## 今回の演習で学ぶこと
この問題では、プロトファイルから自動生成されたインターフェースを満たすように、実際のバックエンド処理（サーバー側）を実装する方法を、以下の3つの重要ポイントに注目して学びます。

**1. 引数としての context.Context**
gRPCのサーバーメソッドは、決まり手として第1引数で必ず `context.Context`（コンテキスト）を受け取る設計になっています。
```go
func (s *server) GetUser(ctx context.Context, req *UserRequest) (*User, error)
```
- `ctx context.Context`: クライアントから「もう待てないから処理をキャンセルして！」と言われた時や、「3秒以内に返事がなければタイムアウト」といった「通信の制御情報」が全てこの中に詰め込まれています。
- `req *UserRequest`: 第2引数には、クライアントから送られてきたリクエストデータ（のポインタ）が入ってきます。

**2. ビジネスロジックと戻り値の型**
送られてきたリクエストの中身を見て、実際にデータを返却するビジネスロジック（中身の手順）です。
```go
if req.Id == 1 {
    return &User{Id: 1, Name: "アリス"}, nil // 成功パターン
}
return &User{Id: req.Id, Name: "不明"}, nil // 見つからなかったパターン
```
- `return &User{...}, nil`: 戻り値は常に「レスポンスのポインタ」と「エラーの有無」の2つセットで返します。
- このように、ただのGoの関数を書くのと同じ感覚で、強力なネットワーク通信の裏側を実装できるのがgRPC最大の魅力です。

**3. インターフェースの満足**
自分が書いた `GetUser` 関数が、gRPCとして正しく認識されるための絶対条件です。
- `.proto` ファイルから自動生成されたGoのコードには、「サーバーを名乗るなら、絶対にこの引数と戻り値の形の関数を持っていなければならない（インターフェースの制約）」という厳しいルールが書かれています。
- 一文字でも型が違えばコンパイルエラーになるため、「繋いでみたらエラーになった」という実行時の致命的なバグを未然に（コンパイル時に）防ぐことができます。




**gRPCのエラーハンドリング**
演習ではシンプルに `nil` や基本的なエラーを返しますが、実際には `status.Errorf(codes.NotFound, ...)` のように、専用のステータスコードを付けて「何が原因で失敗したのか」をクライアントに伝えるのが標準的な作法です。
