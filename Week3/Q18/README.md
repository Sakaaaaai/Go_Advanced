# 問18｜gRPCインターセプタ（Interceptor）

## 目標
HTTPサーバーのミドルウェアに相当する「gRPCインターセプタ」を実装し、全RPCリクエストに対してロギングや認証などの横断的関心事（Cross-cutting Concerns）を挟み込む方法を学びます。

## 今回の演習で学ぶこと
この問題では、Webサーバーの「ミドルウェア」に相当する、全リクエストに対する共通処理を挟み込む「インターセプタ」を、以下の3つの重要ポイントに注目して学びます。

**1. 前処理と FullMethod**
クライアントからのリクエストが、本来の処理（ハンドラー）へ届く「直前」に割り込んで実行される処理です。
```go
// 誰宛のどんなリクエストが来たのかをログに残す
fmt.Printf("開始: %s\n", info.FullMethod)
```
- `info.FullMethod`: 「`/user.UserService/GetUser`」のように、どのサービスのどのメソッドが呼ばれようとしているかという詳細な宛先（パス）が一目でわかる便利なプロパティです。

**2. 本来の処理（ハンドラー）の呼び出し**
前処理（ログ出力や認証チェックなど）が完了した後、いったんせき止めていたリクエストを本来の宛先であるビジネスロジックへ流し込む（バトンを渡す）工程です。
```go
// 本隊へ処理を委譲し、その結果（レスポンスとエラー）を受け取る
resp, err := handler(ctx, req)
```
- `handler(ctx, req)`: これを実行した瞬間、Q16などで実装したあの `GetUser` などの実際の処理が動きます。
- もし認証エラー等で「通したくない」場合は、ここで `handler` を呼ばずに自前でエラーを `return` してしまえば、門前払いにすることができます。

**3. 後処理と結果の返却**
メインの処理が「終わった直後」に、クライアントへ結果を返す前に最後の横槍を入れる処理です。
```go
fmt.Printf("完了: %s\n", info.FullMethod)
return resp, err // 最後に元の結果をそのまま返す
```
- クライアントへ返す直前に、ここで「エラーが起きていないか」のチェックや「処理にかかった時間の計測」などを行うことができます。
- 最後に `resp, err` をそのまま返すことで、クライアント側から見ると「普通にメソッドを呼び出して結果が返ってきた」ようにしか見えず、インターセプタの存在を意識させず（透過的に）機能を追加できます。




**インターセプタの使いどころ**
「アクセスログの出力」「ユーザー認証のチェック」「処理時間の計測」「エラー発生時のリカバリー」など、個別のメソッドに書くと同じコードが重なってしまうような「横断的な処理」を1か所にまとめるために使われます。

## 問題文
`main.go` の `___` の部分を埋めてプログラムを完成させてください。

`loggingInterceptor(ctx, req, info, handler)` を完成させてください：

2. `handler(ctx, req)` でハンドラを呼び出してください。
3. 処理完了のログを出力して、結果を返してください。

## ヒント
- `info.FullMethod` はメソッドのフルパス文字列（例: `/user.UserService/GetUser`）
- `res, err := handler(ctx, req)` で本体処理を実行し、その res と err をそのまま返す
