# 問13｜Redisを用いたキャッシュ層の実装

## 目標
DBへの負荷を軽減するため、インメモリデータストア「Redis」をキャッシュとして利用するパターン（キャッシュ・バイ・パス：Cache-aside Pattern）を学びます。

## 今回の演習で学ぶこと
この問題では、DB負荷を劇的に減らす「Redisキャッシュ（キャッシュバイパスパターン）」を、以下の3つの重要ポイントに注目して学びます。

**1. キャッシュからの取得（Get）**
重くて遅いデータベース（DB）へアクセスする前に、まずは超高速な手元のメモ帳（Redis）に答えが書いてないか探しに行く工程です。
```go
val, err := rdb.Get(ctx, key).Result()
if err == nil { // もしエラーなし（＝データが見つかった）なら
    return val // キャッシュヒット！爆速で結果を返す
}
```
- `rdb.Get`: Redisに「このキーのデータある？」と尋ねます。
- ここで見事にデータを引き当てること（キャッシュヒット）ができれば、DBアクセスという重い処理を1回分まるっとスキップでき、劇的なパフォーマンス向上が得られます。

**2. キャッシュミスの際のDB取得**
惜しくもRedisの手元に答えがなかった場合（キャッシュミス）の、正攻法のバックアップ処理です。
```go
// Redisに無かった（errが発生した）ので、素直にDBへ取りに行く
profile := db.GetFromDB(id)
```
- 最初からDBに取りに行けば確実ですが遅い。だから「無かった時だけDBへ行く」という形にすることで、全体の平均速度を極限まで早める、これが「キャッシュ・バイパス・パターン（Cache-aside）」の神髄です。

**3. 有効期限付きの保存（Set / TTL）**
苦労してDBから取ってきた最新データを、「次、同じ問い合わせが来たらすぐ答えられるように」Redisのメモ帳へ覚え込ませる工程です。
```go
rdb.Set(ctx, key, profile, 10 * time.Minute)
```
- `10 * time.Minute`: ただ保存するだけでなく「10分経ったら忘れろ」という指示（TTL: Time To Live＝有効期限）を出しています。
- キャッシュは高速ですが、いつまでも覚えておくと「本家のDBでは名前が変更されたのに、画面上は古い名前が表示され続ける」という困った現象が起きます。TTLを適切に設定することで、一定時間でわざと記憶を消し、フレッシュな新しいデータをDBに取りに行かせる仕掛けを作ります。




**キャッシュの醍醐味**
「1回目は少し時間がかかるけど、2回目からは一瞬で表示される」という体験は、このキャッシュバイパスパターンによって支えられています。TTL（有効期限）の設計が、エンジニアの腕の見せ所です。
