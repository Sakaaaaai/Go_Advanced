# 問14｜分散ロックの基礎

## 目標
複数のサーバーインスタンスが存在する環境で、ある処理を「同時に1台だけが実行する」ことを保証する「分散ロック（Distributed Lock）」の仕組みをRedisで実装します。

## 今回の演習で学ぶこと
この問題では、複数のサーバーが立ち上がっている環境で、ある処理を「絶対に同時に1台しか実行させない」ための「分散ロック」を、以下の3つの重要ポイントに注目して学びます。

**1. SetNX によるロック取得**
「今からこの処理をやる！」という宣言を、全てのサーバーが見える共有の掲示板（Redis）に書き込むような操作です。
```go
ok, _ := rdb.SetNX(ctx, key, "locked", 5*time.Second).Result()
```
- `SetNX`（Set if Not eXists）: 「もしそこにまだ文字が書かれていなければ、自分の名前を書き込む」という、早い者勝ちのアトミック（途中で割り込まれない）な命令です。
- クレジットカード決済やポイント付与など、「絶対に2回連続で実行されてはいけない処理」のガードマンとして機能します。

**2. ロック取得失敗時のハンドリング**
他の誰かがタッチの差で先に掲示板へ書き込んでいた場合の対応です。
```go
if !ok {
    // 取得失敗＝他のサーバーが絶賛処理中
    return false // 自分は手を出さず、諦めて帰る
}
```
- `ok` には鍵が取れたかどうかの真偽値が入ります。ここで即座に処理を中断させることで、処理の重複（二重課金など）を完璧に防ぎます。

**3. ロックの解放（Del）と有効期限（TTL）**
作業が無事に終わった後の後片付け（ロックの解除）と、最悪の事態への備えです。
```go
defer rdb.Del(ctx, key)
```
- `defer rdb.Del`: 作業が終わったら、自分から鍵を返し（キーを削除し）て、次の人が処理できるようにします。
- `5*time.Second`: 第1ステップの `SetNX` で「5秒」というTTL（有効期限）を付けていました。もし自分のサーバーが処理中に大停電で突然死し、上の `Del` を実行できなくなっても、「5秒後には自動的に鍵が溶けて消滅する」ため、システム全体が永遠に止まってしまう事故（デッドロック）を完全に防ぐことができます。




**なぜ分散ロックが必要か？**
通常の `sync.Mutex` は、1台のコンピューターの中だけでしか効きません。クラウド環境でサーバーが2台、3台と増えたとき、決済処理や集計処理が重なって実行されないようにするために、Redisのような外部の司令塔を使った「分散ロック」が不可欠になります。
