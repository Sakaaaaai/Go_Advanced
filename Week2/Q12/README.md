# 問12｜データベースマイグレーション

## 目標
DBのスキーマ変更をコードとして管理する「マイグレーション」の概念と、`UP`（変更を適用）と `DOWN`（変更を元に戻す）のSQL定義の書き方を学びます。

## 今回の演習で学ぶこと
この問題では、データベースの構造（スキーマ）変更をコードとして安全に管理する「マイグレーション」を、以下の3つの重要ポイントに注目して学びます。

**1. マイグレーションの目的と履歴管理**
本番環境のデータベース（DB）を「手作業で直接いじる」という極めて危険な行為をやめ、安全にチーム開発を行うための作法です。
- スキーマの変更（テーブル作成や、カラム「Age」の追加など）を全てプログラムコードとして残すことで、Gitによるバージョン管理が可能になります。
- 新しくチームに入ったメンバーも、コマンド一発で本番と全く同じ構造のDBを手元に瞬時に再現できるようになり、「誰のパソコンでは動く・動かない」問題が消滅します。

**2. アップ・マイグレーション（UP）の実装**
「新しくこんなテーブルを作りたい」「ここに列を足したい」という前進（UP）の処理です。
```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY, -- 自動で連番が振られるID
    name VARCHAR(50) NOT NULL, -- 50文字以内の絶対必要な名前
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP -- 作成された時間が自動で入る
);
```
- このようにSQL文を使って、データベースの設計図（スキーマ）を組み上げていきます。

**3. ダウン・マイグレーション（DOWN）の実装**
さきほどのUPで適用した変更を「失敗したから取り消して元に戻す（DOWN）」ためのロールバック処理です。
```sql
DROP TABLE IF EXISTS users;
```
- `DROP TABLE`: 指定したテーブルを丸ごと消し去る強力なコマンドです。
- `IF EXISTS`: 万が一「テーブルが既に消えていた」場合にエラーを出して進行がストップするのを防ぐための、プロ必須のフェイルセーフな書き方です。UPとDOWNは必ずセットで用意し、いつでも安全にバージョンを戻せるようにします。




**本番運用の鉄則**
「昨日まで動いていたのに、DBの構造が自分の環境だけ古いから動かない」といったトラブルを防ぐため、マイグレーションファイルを通じた変更管理は近代的な開発において必須の作法です。

## 問題文

2. 定数 `DownMigration` に `users` テーブルを削除するSQL文を書いてください。
