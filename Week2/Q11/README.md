# 問11｜N+1問題の解決（Eager Loading）

## 目標
ORM使用時に頻発する深刻なパフォーマンス問題「N+1問題」を理解し、GORMの `Preload`（Eager Loading）で解決する方法を学びます。

## 今回の演習で学ぶこと
この問題では、ORMを使う際に発生しやすいパフォーマンス低下の原因「N+1問題」とその解決策を、以下の重要ポイントに注目して学びます。

**1. N+1問題とは何か**
ORMの便利さが罠となり、気づかないうちにデータベースへアホみたいな数のクエリ（質問）を投げつけてしまう、最悪のパフォーマンス低下問題です。
```go
// ⛔ 悪い例（N+1問題が発生しているコード）
var users []User
db.Find(&users) // [クエリ1回目]: "SELECT * FROM users" (ユーザー100人取得)

for _, u := range users {
    // [クエリN回目]: ループのたびに裏で "SELECT * FROM orders WHERE user_id = ?" が走る！
    db.Model(&u).Association("Orders").Find(&u.Orders)
}
```
- この悪い例では、ユーザーを100人取得したあと、その100人それぞれの「注文履歴」を取るためにループ内で100回クエリを発行しています。
- 合計「1(ユーザー取得) + N(100回分の注文取得) = 101回」もDBと通信することになり、データが増えるほどシステムが重くなって死滅します。これが「N+1問題」です。

**2. Preload による解決（イーガーローディング）**
最初の段階で「あ、あとで注文データも使うよね」と先回りして、まとめて一挙にデータを取得してくる賢い手法です。
```go
// ✅ 良い例
var users []User
db.Preload("Orders").Find(&users) // 事前に "Orders" も使うことをGORMに伝える
```
- `Preload("Orders")` と付け加えるだけで、GORMが裏側で気を利かせ、「ユーザー一覧を一括取得」した後、さらに「その全員分の注文履歴を一括取得（`IN`句などを使用）」するという、**たった2回のクエリ**で全データを揃えてくれます。
- 101回の通信が2回に減るため、パフォーマンスが劇的に回復します。

**3. レイジー（遅延）とイーガー（一括）の違い**
データの取り方には思想の違いがあり、現代のWeb開発ではイーガーローディングが推奨されます。
- **Lazy Loading（遅延ロード）**: お願いされた時（ループの中などでアクセスされた瞬間）に初めてデータを取りに行く方式。便利に見えてN+1の原因になる「サイレントキラー」です。
- **Eager Loading（一括ロード＝イーガーローディング）**: 最初に「これも使うから持ってきて！」と宣言し、事前に全てを揃えておく方式。`Preload` がまさにこれであり、現代のバックエンドアーキテクチャでは必須のテクニックです。




**パフォーマンスの罠**
N+1問題は、開発環境の数件のデータでは気づきにくく、本番でデータが増えた瞬間にシステムを激重にする「サイレントキラー」です。関連テーブルを扱うときは常に `Preload` を意識しましょう。
